When the same field is checked for null independently in several methods of a class, that repetition is a sign the class is missing a proper representation of the "absent" case. Each additional null-check is another place a future maintainer can forget to add, and another branch a test suite has to cover for no real behavioral reason.

Introducing a Null Object (an implementation of the field's type that provides a safe, no-op or default behavior) — or, in modern Java, wrapping the field in java.util.Optional — lets calling code stop asking "is this null?" and simply invoke the behavior it needs.

Noncompliant Code Example

class OrderProcessor {

  private Discount discount; // may be null

  void applyDiscount(Order order) {
    if (discount != null) {
      order.setTotal(discount.apply(order.getTotal()));
    }
  }

  String describeDiscount() {
    if (discount != null) {
      return discount.getDescription();
    }
    return "No discount";
  }

  boolean hasDiscount() {
    return discount != null;
  }
}

Compliant Solution

class OrderProcessor {

  private Discount discount = Discount.NONE; // never null

  void applyDiscount(Order order) {
    order.setTotal(discount.apply(order.getTotal()));
  }

  String describeDiscount() {
    return discount.getDescription();
  }

  boolean hasDiscount() {
    return discount.isPresent();
  }
}

interface Discount {

  Discount NONE = new Discount() {
    public double apply(double total) { return total; }
    public String getDescription() { return "No discount"; }
    public boolean isPresent() { return false; }
  };

  double apply(double total);
  String getDescription();
  boolean isPresent();
}

Limitations

  • Only direct == null / != null comparisons on fields are detected. Objects.isNull(...), Optional.isPresent(), and instanceof-based null-guard idioms are not currently recognized.
  • The rule counts distinct methods containing a check, not distinct checks — two null-checks on the same field in one method count once.
  • This rule flags a candidate for the Null Object refactoring; it does not verify that a sensible default/no-op behavior actually exists for the type, which is a design judgment left to the developer.
  • Unlike the source paper's regex-based approach, this implementation uses the Java AST and symbol table, so it correctly ignores local variables and parameters that happen to share a field's name, and only matches fields whose null-check recurs across the same class.
